- It turns out the wiggly ghosts alert was sometimes being shown even when the wiggly ghosts weren't doing anything at all, and everything was actually fine. I've updated the code that triggers it to better filter out these false positives so that the wiggly ghosts are only blamed when they actually get involved. Dismissing the alert (a.k.a. "Nevermind") also no longer disconnects the sync account, so you'll have to do that manually if you want the ghosts to wiggle on their merry way.

- Sometimes, when sharing a GIF as a link, the app could freeze while fetching a preview image for the share sheet, which would sometimes result in the app getting killed. I've updated it so that it prefers using a thumbnail it already has on hand, cause there's a pretty good chance you already have one, and it'll fall back to a generic icon if that fails. This means the share sheet shows up instantly, every time… unless it's playing hooky and smoking behind the toilets again.

- I took an opportunity to resolve a long-time issue with iCloud sync, which is that it could crash if the app wasn't able to prepare the folder for the Library. Instead of just force-unwrapping (yes, I know) the directory, it'll actually handle it gracefully, surface the issue in the iCloud settings screen, and try again later.

- It turns out I messed up a while back and broke the 'Browse Logs' screen, basically making it so that selecting a log would give you a whole lot of nothing as options. Well, except for something about a Quick Note, which is about as useful as a punch in the face. Turns out I was passing the wrong thing into the Activity screen, so now it should be working as expected.

- OK, you're all going to want to sit down for this one. It might surprise you to know that GIFwrapped has never had a true database. In part because files, but even when I did start needing to store metadata separately, I never bothered with an actual database (they've hurt me in the past). That changes today. Today your library gets migrated to a database, and that's going to open up a world of possibilities/pain.

- There was a crash where, while applying a rename to a Library item, the code could match the wrong item because it looked things up by path… and I'd forgotten that two items can briefly share the same path while a sync is settling. It'd pull the wrong item out from under itself and crash. Now the code checks the identifier as well, which ensures we have the right thing before applying the rename. Boom. Or less boom, I guess.

- Occasionally, on opening or returning to it, GIFwrapped would freeze for a moment and then crash. This was caused by checking the clipboard for the bookmark in the search drawer, and the fix was to move the code doing the checking off into the background so it doesn't get in the way of the UI. If the clipboard is slow for some ungodly reason, it shouldn't make everything freeze up any more.

- If you ever dragged a GIF out of the macOS app, you might sometimes find that the app locked up while it finished loading. If that took long enough, it could even cause a crash. NOT IDEAL. So now the app starts loading the GIF while you drag, and then hands it over as a file reference, which ensures that nothing gets locked up anymore.

- If you've ever saved a GIF to your library, you might've noticed that doing so could cause duplicates to get created. Which one is real? What even is real? Anyway, I dug in and discovered that the original entry's lack of revision meant that the sync client didn't recognise the item when pulling it back in from the service so it'd create a duplicate, and this could happen repeatedly. Not anymore.

- I got an email recently from someone who kept finding that their Dropbox library kept going missing from their device. It turns out that sometimes, under the right conditions, the iCloud sync client could sometimes discover that it wasn't authenticated properly (because it wasn't at all) and try to disconnect, taking the on-device library with it. One check to see if iCloud should even be signed in, and now it won't try clean itself up when it shouldn't even be there.

- Renaming GIfs were another source of duplicates, mostly because Dropbox would sometimes quietly tweak the filename chosen to ensure that there weren't any conflicts, and GIFwrapped wouldn't recognise it when it pulled the recent list. Now it should recognise the renamed-again file as the same GIF, so no more duplicates. It's a bit of a hack job TBH, but it'll get the job done while I work on a deeper uplift of the Dropbox client.
